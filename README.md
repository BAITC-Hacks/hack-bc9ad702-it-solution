# «Аким на 5 часов» — AI-симулятор управления городом

Интерактивный симулятор, в котором пользователь распределяет единый виртуальный бюджет между пятью городскими направлениями и получает итоговый **Astana Quality of Life Score** вместе с объяснением компромиссов, рисков и рекомендаций.

## Чек-лист задач и функций

### Обязательный MVP

- [ ] Подготовить синтетический датасет условных районов города.
- [ ] Задать одинаковый стартовый виртуальный бюджет для каждого сценария.
- [ ] Создать каталог инициатив с направлениями, стоимостью и ожидаемым эффектом.
- [ ] Реализовать выбор ровно пяти управленческих решений: по одному для транспорта, озеленения, социальной инфраструктуры, безопасности и городского сервиса.
- [ ] Отображать выбранные инициативы, их общую стоимость и остаток бюджета.
- [ ] Запретить добавление решений, если бюджет будет превышен.
- [ ] Рассчитать изменения городских и районных показателей после выбранных решений.
- [ ] Рассчитать итоговый Astana Quality of Life Score.
- [ ] Реализовать AI-анализ: сильные стороны сценария, риски, компромиссы и последствия.
- [ ] Показать понятный итоговый экран со всеми результатами.
- [ ] Добавить инструкцию запуска, описание архитектуры и демонстрационный сценарий в README.
- [ ] Проверить, что другой набор решений меняет итоговый балл.

### Интерфейс и пользовательский путь

- [ ] Стартовый экран с описанием цели, исходного бюджета и правилами игры.
- [ ] Экран/блок состояния районов с ключевыми показателями.
- [ ] Пять разделов для принятия решений.
- [ ] Карточки инициатив с ценой, эффектом и возможными ограничениями.
- [ ] Индикатор бюджета, обновляющийся после каждого выбора.
- [ ] Валидации: нельзя выбрать две инициативы в одном направлении; нельзя завершить сценарий без пяти решений; нельзя превысить бюджет.
- [ ] Итоговый дашборд: общий балл, оценки по направлениям, влияние на районы и AI-вывод.
- [ ] Кнопка «Начать заново», возвращающая пользователя к одинаковым исходным условиям.

### AI и модель расчёта

- [ ] Определить прозрачную формулу базового Astana Quality of Life Score.
- [ ] Задать веса пяти направлений и правила влияния инициатив на показатели районов.
- [ ] Учесть убывающий эффект повторных инвестиций в одно направление.
- [ ] Учесть штрафы за игнорирование критически слабых направлений или районов.
- [ ] Передавать AI структурированный контекст: стартовые данные, решения, бюджет, изменения показателей и итоговый балл.
- [ ] Сформировать шаблон AI-ответа: резюме, сильные стороны, риски, компромиссы, последствия и улучшения.
- [ ] Обеспечить запасной детерминированный текстовый анализ, если AI API недоступен.

### Качество, данные и демонстрация

- [ ] Не использовать персональные, чувствительные или закрытые данные.
- [ ] Зафиксировать стартовые данные и бюджет для честного сравнения команд.
- [ ] Покрыть расчёт бюджета и итогового балла автоматическими тестами.
- [ ] Проверить сценарий превышения бюджета.
- [ ] Проверить сценарий с пятью допустимыми решениями.
- [ ] Подготовить 2–3 демонстрационных сценария с разными результатами.
- [ ] Оформить презентационные скриншоты или короткое демо.

### Опциональные функции

- [ ] Сравнение нескольких команд или сохранённых сценариев.
- [ ] Карта/графики изменений показателей по районам.
- [ ] AI-рекомендации по перераспределению бюджета.
- [ ] Непредвиденное городское событие с необходимостью скорректировать план.
- [ ] Генерация краткой презентации выбранного сценария.

## Подробное описание того, что нужно сделать

### 1. Определить границы MVP

Цель MVP — за одну короткую сессию дать пользователю почувствовать компромиссы городского управления. Пользователь получает те же стартовые условия, что и все остальные: фиксированный бюджет, одинаковые данные районов и один общий каталог инициатив. Затем он выбирает по одной инициативе в каждом из пяти обязательных направлений:

1. транспорт;
2. озеленение;
3. социальная инфраструктура;
4. безопасность;
5. городской сервис.

После пятого решения система пересчитывает показатели, показывает итоговый балл и объясняет, почему этот сценарий получился сильным или рискованным.

**Критерий готовности:** основной путь проходит без ручных действий разработчика: старт → пять решений → контроль бюджета → результат с объяснением.

### 2. Подготовить синтетические данные

Нужно создать небольшой, понятный и воспроизводимый набор данных, например для 5–8 условных районов Астаны. Это не реальные административные данные, а учебная модель.

Для каждого района следует хранить показатели по шкале 0–100:

| Поле | Значение |
| --- | --- |
| `district_id`, `name` | Идентификатор и название условного района |
| `transport_load` | Загруженность транспорта: больше — хуже |
| `green_coverage` | Доступность зелёных зон: больше — лучше |
| `social_infrastructure` | Доступность школ, садов, поликлиник: больше — лучше |
| `safety` | Уровень безопасности: больше — лучше |
| `city_services` | Качество городских сервисов: больше — лучше |
| `population_weight` | Вес района при подсчёте общего результата |

Отдельно нужен каталог мероприятий. Каждая инициатива содержит идентификатор, направление, название, описание, условную стоимость, затрагиваемые районы, эффект на показатели и возможные риски. Пример: «Выделенная автобусная полоса в Северном районе» стоит 25 млн условных единиц, снижает `transport_load` на 12 пунктов и слегка повышает `city_services`.

**Критерий готовности:** данные хранятся в репозитории в JSON/CSV и загружаются приложением без внешних закрытых источников.

### 3. Настроить бюджет и правила выбора

Всем пользователям должен выдаваться одинаковый бюджет — например, **100 млн условных единиц**. Значение хранится в конфигурации, а не задаётся пользователем. Это обеспечивает честное сравнение сценариев.

Логика выбора должна:

- разрешать выбрать только одну инициативу в каждом из пяти направлений;
- показывать стоимость каждого выбора и остаток бюджета;
- блокировать карточку, если её выбор превысит бюджет;
- не давать открыть итоговый результат, пока не выбраны все пять направлений;
- позволять заменить решение, пересчитав бюджет;
- позволять сбросить сценарий до исходного состояния.

**Критерий готовности:** сумма решений никогда не превышает бюджет ни визуально, ни на уровне бизнес-логики.

### 4. Реализовать модель влияния решений

Инициативы должны менять не только общий счёт, но и конкретные показатели районов. Для каждой выбранной меры необходимо применить её эффект к затронутым районам, ограничив значения диапазоном от 0 до 100.

Например:

- транспортное решение уменьшает транспортную нагрузку, но может требовать значительной части бюджета;
- озеленение повышает доступность зелёных зон и может косвенно улучшать комфорт;
- социальная инфраструктура повышает доступность ключевых услуг;
- безопасность повышает соответствующий показатель, особенно в районах риска;
- городской сервис повышает качество обращений, уборки, освещения или цифровых услуг.

Чтобы симулятор выглядел реалистичнее, в формулу можно добавить:

- приоритет для районов с худшими исходными значениями;
- убывающую отдачу, если вложения концентрируются в уже сильном направлении;
- штраф за критически просевшее направление;
- небольшой бонус за сбалансированное улучшение разных сфер.

Эти правила должны быть явно описаны в коде и README: AI не должен быть единственным источником вычисления итогового балла.

### 5. Рассчитать Astana Quality of Life Score

Итоговый балл должен быть детерминированным и воспроизводимым. Базовый вариант — нормализованная взвешенная сумма показателей всех районов:

```text
районный score =
  0.25 × (100 − transport_load) +
  0.20 × green_coverage +
  0.20 × social_infrastructure +
  0.20 × safety +
  0.15 × city_services

Astana Quality of Life Score =
  взвешенное среднее районных score
  + бонус за баланс
  − штрафы за критические риски
```

Вес района берётся из `population_weight`. Коэффициенты можно менять после тестовых прогонов, но они должны быть едиными для всех пользователей. В интерфейсе нужно показать общий балл, изменение относительно стартового состояния и оценки по каждому направлению.

**Критерий готовности:** если изменить хотя бы одно решение, пересчитываются показатели и итоговый Score.

### 6. Добавить AI-анализ

AI не заменяет расчётную модель, а объясняет её результат человеческим языком. В AI передаётся структурированный набор данных: исходные показатели, выбранные инициативы, расходы, остаток бюджета, изменения по районам, итоговый балл, сильные и слабые направления.

Ожидаемый ответ AI должен содержать:

- краткое резюме сценария;
- сильные стороны выбранных решений;
- риски и нерешённые проблемы;
- ключевые компромиссы: что улучшили и чем пожертвовали;
- вероятные последствия для районов;
- 2–3 практичные рекомендации для улучшения сценария.

Важно запретить AI придумывать несуществующие цифры: в промпте следует потребовать опираться только на переданные данные и явно отмечать допущения. Если доступ к модели недоступен, приложение показывает сформированный по правилам анализ, чтобы MVP оставался работоспособным.

### 7. Собрать интерфейс

Интерфейс должен вести пользователя по сценарию без обучения. Рекомендуемая структура:

1. **Стартовый экран** — правила, бюджет, кнопка запуска.
2. **Состояние города** — краткие карточки районов и проблемные зоны.
3. **Пять решений** — вкладки или последовательные шаги с инициативами.
4. **Панель бюджета** — всегда видна, показывает расходы и остаток.
5. **Итог** — общий Score, изменения по направлениям/районам, AI-анализ и кнопка перезапуска.

Для хакатона особенно важна наглядность: используйте цветовые индикаторы, простые столбчатые диаграммы или карту районов. При этом итоговые цифры должны оставаться читаемыми и объяснимыми.

### 8. Предложенная техническая архитектура

Минимальная архитектура может состоять из следующих модулей:

| Модуль | Ответственность |
| --- | --- |
| Frontend | Интерфейс выбора решений, отображение бюджета и результатов |
| Simulation engine | Проверка правил, применение эффектов инициатив и расчёт Score |
| Data layer | Загрузка синтетических районов, инициатив и конфигурации бюджета |
| AI analysis service | Формирование контекста, вызов AI и запасной анализ |
| Tests | Проверка бюджета, формулы Score и сценариев |

Подходящий стек для быстрого прототипа: React/Vite или Next.js для интерфейса, TypeScript для модели, локальные JSON-файлы для данных и API-обработчик для AI. Если AI API недоступен, сервис должен возвращать детерминированный fallback-ответ.

### 9. Протестировать ключевые сценарии

До демо необходимо проверить минимум следующие случаи:

- все пользователи начинают с одинаковым бюджетом и одинаковыми данными;
- нельзя выбрать инициативу сверх остатка;
- можно заменить решение, и бюджет корректно пересчитывается;
- без пяти решений нельзя получить финальный результат;
- пять допустимых решений формируют Score и объяснение;
- разные наборы решений дают разные итоговые показатели;
- AI получает корректные числа и не влияет на базовый расчёт;
- при ошибке AI API пользователь всё равно получает результат.

### 10. Подготовить README и демо

После реализации README должен быть дополнен фактическими командами запуска, переменными окружения для AI, описанием структуры папок, источником/лицензией синтетических данных и скриншотами. Для защиты подготовьте один сбалансированный и один рискованный сценарий: это наглядно докажет, что решения действительно меняют модель.

## Definition of Done

Проект готов к сдаче, когда пользователь может локально запустить приложение, получить одинаковые стартовые условия, выбрать пять допустимых инициатив без превышения бюджета, увидеть изменённые показатели районов и итоговый Astana Quality of Life Score, а также прочитать понятный AI-анализ сильных сторон, рисков и вариантов улучшения.
